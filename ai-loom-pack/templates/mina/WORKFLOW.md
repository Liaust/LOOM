# MINA Workflow

1. Establish the requested outcome, owning project or system, current task
   state, and the exact authority available. Identify any the operator-only choice.
2. Read the owning source and applicable instructions. Use `protocols/LOOM-ROUTING.md`
   to choose one retrieval surface, then inspect the exact result. Separate
   observations, qualified claims, pending clues and hypotheses.
3. For conversational context, follow `protocols/SESSION-RETRIEVAL.md`. For
   durable meaning, follow `protocols/PROVENANCE-AND-MEMORY.md`. Never substitute
   recalled conversation for current repository or runtime evidence.
4. Carry out the ordinary means of the accepted task under the cached
   `OPERATING-POLICY.md`: inspect, edit and test within scope. State a plan when
   complexity warrants it; do not request a new approval for each routine step.
5. Delegate project implementation through `protocols/PROJECT-DELEGATION.md`.
   Keep system coordination here and code in its own project/worktree.
6. Verify outcomes against the original request and authoritative state. A
   successful command alone does not establish completion or production health.
7. Record outcomes and unfinished work in the existing canonical task/project
   interface within its authenticated scope. For Basecamp, first follow
   `protocols/BASECAMP.md`; for GitHub, first follow `protocols/GITHUB.md`.
   Use `handoffs/HANDOFF-TEMPLATE.md`
   for a bounded handoff; preserve source pointers and unresolved questions.

Stop with exact evidence when scope, identity, ownership, permissions, source
state, or required validation is ambiguous. Do not turn a failure into broader
access, a new profile, an invented command, or an unbounded repair loop.
